### Why external scanners report the site "unreachable"
`X-Frame-Options: DENY` is served platform-wide. Security-header scanners that embed the page in an iframe (rather than fetching it) report a connection/rendering failure. This is expected platform behavior and does not affect Google or AI crawlers (verified above). **Do not change this header** — it is a legitimate anti-clickjacking control.

## 1. SEO & AI Discoverability Findings

### CRITICAL — Homepage head is stale and incomplete (dashboard override)
The served `<head>` is generated by the platform's SEO & GEO settings and **overwrites** the custom index.html tags. Live today:
- **Title:** `Same Day Recycling` — no keywords, no service or geo terms.
- **Description:** still the old copy — *"Professional junk and furniture removal services for Vancouver and the Lower Mainland…"* — inaccurate (Vancouver-only framing, not approved copy).
- **Open Graph / Twitter:** same stale description; og:image is the logo, not the branded banner.
- **No canonical tag is served at all.**
- **llms.txt summary** is generated from that same stale description.

**Fix (no code changes needed):** update Marketing > SEO & GEO > Meta tags to the approved values, then republish:
- Title: `Same Day Recycling | Junk Removal & Recycling in Canada`
- Description: `Same Day Recycling connects customers with junk removal, furniture pickup, and responsible recycling services. Explore service availability and request a quote.`
The page source (index.html + Home.jsx) is already aligned to these values.

### HIGH — All non-homepage titles/descriptions are client-side only
Every inner page (city pages, services, blog) injects its title/description/JSON-LD via JavaScript. Googlebot renders JS so it is covered, but non-rendering AI crawlers (GPTBot, PerplexityBot) see no per-page metadata. Acceptable near-term; a pre-rendering/SSG pass would be the structural fix later.

### WORKING
- JSON-LD graph on homepage: Organization, WebSite, LocalBusiness with 5 verified cities (Vancouver, Burnaby, Surrey, Richmond, Coquitlam), ContactPoint — correct, no nationwide claims.
- robots.txt correctly separates public vs. private paths.
- Sitemap fresh (65 URLs, current lastmod); legacy /vancouver issue no longer present.
- Verified-only areaServed maintained; unverified regions labelled Partner Onboarding / Coming Soon.

### MINOR
- `/manifest.json` 302-redirects to the platform manifest endpoint — harmless.
- Unknown paths return HTTP 200 (client-side "not found") — soft-404 risk in Search Console; monitor.
- A few reviews reference cities outside the 5 active service areas (Kamloops, Kelowna) — keep these attributed to partner markets to stay accurate.

## 2. Customer Experience (Phase 2)

### Verified working
- **Quote calculator → server pricing:** live-tested. `quoteEstimate` returned a correct range ($289–$350 for sofa + fridge) in 144 ms, using city-specific PricingSettings with defaults fallback.
- **Booking flow end-to-end:** live-tested. Booking created with correct fields, status history set, **owner email sent ✓, customer confirmation email sent ✓**. (Test record was deleted after the audit.)
- **Contact form:** validates email, stores nothing (email-only), forwards to owner — logic sound.
- **Analytics events wired:** `booking_submitted` fires from BookingForm (both Base44 analytics and GA4 gtag); quote calculator fires `quote_calculated` (see bug below).
- **Public page surface:** all key routes return 200 (city pages, pricing, software, blog, services, coverage, directory, gallery, recycling centers).
- **Reviews:** 10 records, all approved, city-attributed.

### Issues
| Severity | Issue |
|---|---|
| **HIGH** | `QuoteCalculator` calls `base44.analytics.track("quote_calculated", {...})` with a string — the SDK signature is `track({ eventName, properties })`. The quote event is likely **not being recorded**, so the quote-to-booking KPI is blind. One-line fix. |
| **HIGH** | No QuoteLead records exist (0). Either the calculator never persisted a lead by design or lead capture is broken — verify the quote → "send me this quote" path with a real submission. |
| MEDIUM | No rate limiting / honeypot on any public form (booking, contact, quote, review) — spam and abuse exposure, and direct booking cost (emails per submission). |
| MEDIUM | Customer photos in receptionist chat upload to public storage (anyone with the URL can open them). Should be UploadPrivateFile + signed URLs. |
| LOW | Only 2 real bookings ever recorded (both cancelled); no completed job yet — review-request and payout flows are untested in practice. |

## 3. Business Operations (Phase 3)

### Authentication & permissions — SOUND
- Admin routes gated by ProtectedRoute; admin-only RLS on Booking, PaypalTransaction, PricingSettings, MetricTargets, RoutePlan, ContractorApplication.
- Licensee isolation correct: SoftwareLicense, LicenseCustomer, LicensePickup, LicenseInvoice readable/writable only by the owning licensee's email or admin. White-label and license entities are properly separated.

### Data & reporting
- **Real production data, not mock:** analytics come from GA4 (live), internal Visit tracking (1,238 records), Booking/Review/RecyclingFact/CitySeo entities. RecyclingCenter: 112 records; ContentPost: 21.
- Booking pipeline exists (new → confirmed → scheduled → completed) with status history; dispatch/assignment fields present.
- Gaps: GoogleReviewsMeta empty (Google review sync not configured — needs GOOGLE_PLACES_API_KEY); Partner records empty; RoutePlan empty (route optimization never used in production).

### Payments — NOT PRODUCTION-READY
| Severity | Issue |
|---|---|
| **CRITICAL** | 0 PaypalTransaction records ever — no successful payment has ever been processed. Credentials are believed to point at the **live** PayPal API while `PAYPAL_MODE` routes requests to **sandbox** (`api-m.sandbox.paypal.com`), so real checkouts fail. Fix: set `PAYPAL_MODE` to match the credential environment. |
| **HIGH** | License activation still triggers on PayPal status `APPROVED` as well as `ACTIVE` (paypalCheckout line 245). `APPROVED` means the customer agreed but billing hasn't started — activation should require `ACTIVE`. |
| **HIGH** | No PayPal webhook receiver: cancellations, suspensions, and failed payments never flow back — churned licensees keep dashboard access indefinitely. |
| MEDIUM | License provisioning (account invite) happens inside verify_subscription — works, but with webhooks absent, a user who closes the browser after approval never gets provisioned. |

### Multi-operator readiness — FOUNDATION PRESENT
- License entity model (starter/growth/network tiers, monthly/annual, pay-token payment links) is complete and payment-wired.
- Licensee dashboard modules exist (customers, scheduling, dispatch, invoicing) with correct data isolation.
- Not yet present: per-license branding (logo/colors/service area), automated billing-status management, partner records. Blockers are the payment issues above.
